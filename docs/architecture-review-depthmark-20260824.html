Make date-scoped publication a deep module

The repository has a solid source-isolated medallion architecture and a passing unit suite. The largest remaining risk is that admission, failure status, staging cleanup, and publication correctness are spread across shallow interfaces. The top recommendation is to deepen that boundary before adding more analytical surface area.

Highest risk
Partial success

FotMob Bronze can log errors and return zero rows; some contract checks then skip zero-row tables.

Largest leverage
Publication seam

One deep Module can own admission, stage lifecycle, commit markers, cleanup, and run outcomes.

What is working
286 tests pass

Oddspedia has strong checksums, date locks, staged Bronze publication, and explicit source boundaries.

Top recommendation: deepen the date publication Module

flowchart LR A[Artifacts / SQL jobs] --> B[Admission Interface] B --> C[DatePublication Module] C --> D[Stage + validate] D --> E[Commit marker] E --> F[Scoped target] C --> G[Run result + metrics] C -.-> H[ClickHouse Adapter]

Problem

The current Interface is spread over loaders, ClickHouse helpers, stage replacement code, and subprocess orchestration. Implementations can silently convert missing tables, malformed files, insert failures, and incomplete reads into a successful-looking run.

Deep design

Create a Module with a small explicit Interface: admit, stage, validate, publish, recover, and report. Keep the ClickHouse Adapter behind a Seam. Return typed outcomes such as admitted, quarantined, failed, published, and partially committed.

Leverage

One change improves FotMob Bronze, Silver, Gold, and future Oddspedia layers.

Locality

Failure semantics live beside the publication Implementation instead of being reconstructed by every caller.

Substitutability

A fake Adapter can test publication behavior without a live warehouse.

Architecture candidates

Strong · local-substitutable

Bounded raw artifact ingestion

Files: src/fotmob/bronze/loader.py, src/fotmob/bronze/base_storage.py. Problem: all DataFrames are accumulated in memory, and member failures can produce partial input. Solution: an ArtifactBatchReader Implementation yields bounded chunks and a manifest with complete, partial, or quarantined status. Wins: lower memory, replayability, clearer backpressure, and better data locality.

Strong · local-substitutable

Explicit warehouse contract seam

Files: clickhouse/*ddl, signal catalogs, src/warehouse/contracts.py, src/warehouse/quality.py. Problem: some identity contracts are inferred from ClickHouse ORDER BY text. Solution: one contract registry or generator exposes grain, identity, scope, nullability, and version policy. Wins: deterministic validation, safer schema evolution, and fewer regex-based assumptions.

Worth exploring · remote-owned

Run controller for lifecycle and observability

Files: scripts/orchestration/pipeline.py, ClickHouse client, locks, health reporting. Problem: subprocesses have no timeout or process-group cancellation, and query execution has no shared query ID or bounded retry policy. Solution: a RunController Module owns timeout, lock, retry, metrics, and alert Adapters. Wins: predictable scheduling, easier incident diagnosis, and bounded resource use.

Worth exploring · local-substitutable

Incremental derived-data base

Files: src/fotmob/silver/service.py, src/fotmob/gold/dml_runner.py, src/warehouse/scoped_replace.py. Problem: a date-scoped run advertises a date output but stages full-history calculations. Solution: materialize reusable date/season bases and declare lookback windows per job. Wins: lower ClickHouse scans, shorter reruns, and a clearer performance contract.

Recommended order

  1. P0: fail closed for FotMob Bronze admission and truncate/reload errors.
  2. P1: fix container startup/scheduler behavior, add subprocess and ClickHouse timeouts, and add CI gates.
  3. P1: deepen the publication Module and bounded artifact ingestion seam.
  4. P2: make warehouse contracts explicit, remove SELECT *, and reduce full-history recomputation.
  5. P3: standardize formatting/type tooling, pin dependencies, refresh readiness documentation, and complete the Oddspedia roadmap when product scope requires it.
