Oddspedia Artifact Contract

Explicit listing/payload interface

Validate the observed football shape, preserve unknown source fields, and write the caller's object unchanged via one atomic implementation.

Problem: the current model omits real football fields such as score and most outcome shapes, while the writer guesses artifact type and can add defaults.

Solution: make callers select the artifact contract explicitly, validate the complete observed shape, and separate validation from serialization so validation never rewrites source JSON.

  • Locality: shape knowledge stays in one module.
  • Leverage: scraper, tests, and future readers cross the same interface.
  • Tests: assert persisted bytes/keys remain compatible while bad roots and nested odds fail.

ADR: aligns with ADR 0021 source fidelity; no conflict.

After

ScrapeManifest

Validated state transitions + unknown-field round trip

Legacy shapes remain readable, interrupted states remain resumable, and future metadata survives read-modify-write.

Problem: wrong root types fail late, future top-level fields are silently dropped, and total is easy to confuse with the priority-selected scope.

Solution: validate field types at load/save, preserve unknown fields, and document the existing full-inventory versus selected-scope semantics without migrating stored manifests.

  • Locality: compatibility and invariants live with state transitions.
  • Leverage: every resume and concurrent checkpoint inherits safe parsing.
  • Tests: cover unknown-field preservation, legacy in_progress, corrupt types, and interrupted retries.

ADR: preserves ADR 0022's compact summary and per-date audit role.

3. Add an inclusive date-range interface to Oddspedia workflows

SelectedImplemented

Files/modules: Oddspedia scrape CLI, Bronze loader, resolver, canonical wrappers, tests, runbook docs.

Before

flowchart LR
  D[--date] --> R[run]
  M[--month] --> R
  C[current month] -->|future days| X[entire scope rejected]

After

flowchart LR
  D[--date] --> V[Validated date scope]
  M[--month] --> V
  B[--start-date + --end-date] --> V
  V --> R[resume-safe per-date run]
  M -->|current month| T[through today]

Problem: operators must choose a whole month or invoke many dates manually, and selecting the current month currently rejects all work because later days are in the future.

Solution: use the repo's established --start-date/--end-date interface and clip only a current-month selector through today.

  • Locality: one date resolver owns ordering and future-date rules.
  • Leverage: collection, load, and resolution can process the identical slice.
  • Tests: cover inclusive ranges, reversed ranges, current-month clipping, and old selectors.

Operational considerations

  • The schemas intentionally allow additive source fields. Tightening or removing an existing field is a breaking raw-contract decision and should be versioned intentionally.
  • An interrupted legacy manifest may place an event in both failed and in_progress. It remains readable so the normal retry/state transition can heal it; historical manifests are not rewritten merely for cleanup.
  • The workspace had another active Oddspedia process during final verification. Corpus validation was therefore read-only and time-scoped; no artifact was restored, reformatted, or overwritten by this remediation.
  • The external Draft 2020-12 schema suite uses the development-only jsonschema dependency. Runtime scraping continues to use Pydantic and does not add a schema field or envelope to source JSON.

Final architecture

Immutable source JSON behind a deep, explicit persistence seam

Candidates 1–3 are implemented together. The resulting design keeps raw Oddspedia contracts source-faithful, makes manifest evolution additive and resumable, and gives operators one efficient bounded-date interface from collection through resolution.
