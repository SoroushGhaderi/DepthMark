Findings, ordered by severity

Critical · P0

Repeatable warehouse setup is data-destructive

Resolved 2026-10-10

Evidence: Gold setup collects every SQL file below gold/ddl and excludes only filenames containing optimize or beginning with scenario_ (scripts/clickhouse_setup_common.py:331-340). Seventeen selected files contain DROP TABLE; for example, signal DDL drops tables before creating them (create_table_match_shooting_goals.sql:3-5) and activation DDL drops the serving table (create_table_signal_activations.sql:1-5). The Docker entrypoint invokes setup on startup (docker/docker-entrypoint.sh:15-17).

Impact: a routine container restart or schema setup can erase Gold signal and activation rows. The existing production-readiness note addresses routine OPTIMIZE, but does not remove these destructive Gold DDL statements (docs/PRODUCTION_READINESS_REVIEW.md:36-40).

Recommendation: make normal setup strictly idempotent and limited to CREATE DATABASE IF NOT EXISTS, CREATE TABLE IF NOT EXISTS, and safe additive migrations. Move drops/rebuilds into a separately named, explicitly confirmed migration or rebuild command. Add an integration test that inserts a sentinel Gold row, runs setup twice, and asserts the row survives.

Resolution (2026-10-10): implemented as described in ADR 0026 and the remediation log; the sentinel-row integration test remains open.

Warning · P1

The default Docker entrypoint waits on the wrong hostname and has no timeout

Resolved 2026-10-10

The entrypoint polls http://clickhouse:8123/ping forever (docker/docker-entrypoint.sh:6-11), while Compose defines the service as depthmark-clickhouse (docker-compose.yml:42-48) and does not declare a clickhouse network alias. A failed setup also exits because of set -e, so the warning branch at lines 18-22 cannot provide recovery. Use the actual service name or an explicit alias, perform an authenticated health check, and fail with a bounded timeout and actionable diagnostics.

Resolution (2026-10-10): the entrypoint no longer waits for ClickHouse or runs setup (ADR 0026); setup is an explicit operator step.

Warning · P1

The scheduler profile does not actually run a scheduler

Resolved 2026-10-10

The scheduler service mounts a missing ./crontab path (docker-compose.yml:126-155), has no command that starts cron, and does not mount the clickhouse/ SQL tree. The image default is only python -m src.cli --help (docker/Dockerfile:103-110). Choose one deployment model: remove this profile and document an external scheduler, or add a real scheduler image/command, an existing schedule file, lock/overlap policy, and health/alert behavior.

Resolution (2026-10-10): DepthMark uses an external scheduler (ADR 0027); the misleading Compose profile is removed and the host scheduling contract is documented.

Warning · P1

Production Compose defaults expose databases with predictable credentials

Resolved 2026-10-10

Compose publishes MongoDB and ClickHouse ports on all host interfaces (docker-compose.yml:8-17, docker-compose.yml:42-56) and falls back to orbit_pass/fotmob_pass when variables are absent. The file explicitly discusses production deployment at lines 1-3. The setup script rejects insecure ClickHouse credentials outside local development, but the database containers themselves still boot with these defaults (scripts/clickhouse_setup_common.py:63-115). Require production secrets at Compose/config validation time, bind local ports to loopback, and keep production exposure behind private networking/TLS.

Resolution (2026-10-10): Compose now requires database passwords from .env and binds published ports to 127.0.0.1 by default (ADR 0005 update). Production exposure stays a separate deployment-manifest concern.

Warning · P1

Warehouse runtime grants are still broader than an application identity should have

Open

RUNTIME_DATABASE_PRIVILEGES grants DROP TABLE, TRUNCATE, and OPTIMIZE across every warehouse database (scripts/clickhouse_setup_common.py:36-52, scripts/clickhouse_setup_common.py:271-284). Split identities into bootstrap/migration, ingestion, derived-load, reporting, and maintenance roles. This also makes accidental destructive calls fail closed.

Warning · P1

Scoped publication is staged, but not atomic across tables

Resolved 2026-10-10

The warehouse replacement Module stages all jobs, then commits target tables one at a time (src/warehouse/scoped_replace.py:86-123). If a later commit fails, earlier tables remain committed and the system only logs “rerun the same scope to converge.” Readers can therefore observe a mixed-version Silver/Gold scope. Add a durable run/batch manifest and a publication marker; make consumers read only the last published run, or publish per-layer watermarks after every table has passed validation.

Resolution (2026-10-10): scoped batches now record a durable per-partition publication status (ADR 0028), and DepthMark readers fail closed on unpublished partitions; external readers can apply the same query.

Warning · P1

The built wheel omits most runtime packages

Resolved 2026-10-10

The packaging configuration declares only src and scripts (pyproject.toml:73-85). A local wheel build confirmed that nested packages such as src.fotmob, src.integrations, and src.warehouse are not in the wheel, even though the CLI dispatches to them (src/cli.py:102-151). Use package discovery, add an install smoke test that runs depthmark --help and one dry-run command from a clean environment, and make the Docker build use the same installable artifact.

Resolution (2026-10-10): package discovery now covers every code package, editable checkout installs are the documented supported mode, and the CLI fails with an actionable message outside a checkout.

Warning · P2

There is no automated CI/CD or SQL/migration test gate

The prior readiness record still reports no CI workflow and no SQL logic or migration-idempotency tests (docs/PRODUCTION_READINESS_REVIEW.md:81-90). The repository scan found no GitHub/GitLab/Jenkins configuration and no SQL test files. Add a PR gate for package build/import, Ruff, Black, mypy, unit tests, SQL parsing/linting, schema bootstrap idempotence, and a small ClickHouse integration suite. Add a deployment gate for destructive DDL and credential validation.

Warning · P2

The quality baseline is not clean and coverage is not enforced

The full suite passes, but generated coverage is 52%; critical modules such as src/fotmob/bronze/match_processor.py and src/fotmob/bronze/storage.py are mostly unexecuted. Ruff reports 162 errors, Black would reformat 33 files, and mypy reports 205 errors in 30 source files. The configuration has no fail-under threshold (pyproject.toml:151-169). Establish a staged baseline: first clean the import-path and typing contract, then enforce formatting/lint, then require targeted coverage for ingestion, staging, publication, and failure paths.

Warning · P2

Dependencies are floating and the image is not reproducible

Both the project metadata and requirements file use open-ended >= constraints (pyproject.toml:28-52, requirements.txt:5-66), while Docker installs the latest matching versions at build time (docker/Dockerfile:22-25). Generate a lock file with hashes, separate runtime and development dependencies, and build/publish from a pinned lock in CI.

Warning · P2

The source interfaces drift from concrete implementations

The shared protocols require methods such as save_match/load_match and process/validate (src/core/interfaces.py:29-169), while concrete FotMob classes expose different operations such as save_matches_batch, process_all, and fetch_match_details (src/fotmob/bronze/base_storage.py:34-69, src/fotmob/bronze/match_processor.py:108-110). This is why mypy reports abstract/incompatible implementations. Define interfaces around real workflow behavior, or stop inheriting from protocols and use narrow internal seams.

Warning · P2

Repeated FINAL scans and SELECT * will become expensive as Gold grows

The repository scan found FINAL in 40 source/SQL files and SELECT * in five. The scoped replacement path copies whole rows with SELECT * and FINAL (src/warehouse/scoped_replace.py:154-176), while Gold SQL also uses wide intermediate projections (representative Gold SQL:98-130). Prefer explicit columns, validate schema drift, and reserve FINAL for controlled reconciliation or pre-merged source views.

Suggestion · P3

Retention and storage policy are implicit

No ClickHouse SQL file declares a TTL. Representative Bronze, Silver, and Gold tables define partitions and ordering but no retention policy (bronze.general:36-43, silver.match:51-55, gold_scenarios:15-18). Decide and document whether history is permanent, tiered, or retained by source/date; then add TTL or an explicit archive/maintenance contract where appropriate.

Architecture-deepening candidates

Each candidate is a proposal to make a Module deeper: a smaller Interface with more behavior hidden behind it. These are not final interfaces yet; they are the seams worth exploring.

StrongLocal-substitutable

1. Make warehouse setup a deep, non-destructive Module

Files: scripts/clickhouse_setup_common.py, clickhouse/gold/ddl/**, docker/docker-entrypoint.sh.

Problem: the setup caller must understand file discovery, legacy folders, exclusions, DDL ordering, and which SQL files are destructive. Solution: concentrate admission, idempotence checks, migration classification, and safety confirmation behind one setup workflow.

Before

flowchart LR A[Docker restart] --> B[setup all gold/ddl SQL] B --> C[DROP TABLE] C --> D[CREATE TABLE] B --> E[No publication marker]

After

flowchart LR A[Restart] --> B[Safe setup Module] B -. seam .-> C[Idempotent bootstrap adapter] B -. seam .-> D[Explicit migration adapter] B --> E[Schema/version check] E --> F[Ready marker]
  • Locality: destructive SQL and setup policy live in one place.
  • Leverage: every container, operator command, and CI test gets the same safety behavior.
  • Interface: callers ask for a safe setup or an explicitly approved migration.
  • Tests: run setup twice against a local ClickHouse substitute and preserve sentinel rows.
ADR callout: revisit the setup contract documented as safe in docs/PRODUCTION_READINESS_REVIEW.md; the current DDL inventory still contains destructive Gold operations. Resolved by ADR 0026 (create-only setup, schema-drift check, explicit Table Recreation).
StrongLocal-substitutable

2. Make date-scoped publication a deep Module

Files: src/warehouse/scoped_replace.py, Silver/Gold services, load-status tables.

Problem: staging, row-count checks, replacement, cleanup, and partial-failure semantics are implemented, but readers have no durable publication marker. Solution: let one Module own run identity, stage cleanup, validation evidence, publish state, and recovery.

Before

flowchart LR A[SQL job] --> B[Stage] B --> C[Commit table 1] C --> D[Commit table 2] D --> E[Failure] E --> F[Mixed-version readers]

After

flowchart LR A[SQL jobs] --> B[Publication Module] B --> C[Stage all] C --> D[Validate batch] D --> E[Publish marker] E --> F[Readers select published run]
  • Locality: recovery and cleanup logic stop leaking into callers.
  • Leverage: one publication contract serves Bronze admission, Silver, Gold, and activation rebuilds.
  • Tests: interface tests cover empty scope, partial commit, retry, and stale stage cleanup.
StrongTrue external

3. Split Oddspedia intake into a deep workflow Module

Files: src/oddspedia/scraping/cli.py (2,106 lines), match_scraper.py (3,563 lines), match_collector.py (1,848 lines).

Problem: CLI parsing, browser lifecycle, discovery, extraction, retries, audit, metrics, manifest updates, and persistence are spread across very large Modules; the CLI configures logging at import time (cli.py:25-109). Solution: keep Selenium as an Adapter behind a workflow seam that owns the accepted inventory → scrape → audit → manifest contract.

Problem: the package CLI is a stable facade, but packaging omits nested packages and the scripts still own path bootstrapping. Solution: use package discovery, move reusable command behavior behind a package seam, and keep thin compatibility wrappers only at the filesystem edge.

5. Let Gold catalogs generate and validate their contracts

Files: scripts/gold/signal/catalogs/*.md, clickhouse/gold/ddl/signals/**, clickhouse/gold/dml/signals/**, and warehouse contracts.

Problem: the repository documents hundreds of signals and keeps metadata, DDL, DML, and row identities in separate surfaces. Solution: treat catalog frontmatter as the contract source and generate or validate DDL/identity projections, while keeping business transformation SQL explicit.

flowchart LR A[Signal catalog] --> B[Contract validator] B --> C[DDL identity] B --> D[DML target] B --> E[Activation metadata] F[Business SQL] --> D

  • Keep the source-domain separation intact; this is a catalog seam, not a provider framework.

Top recommendation

Fix setup safety before adding more warehouse surface area

The source-isolated architecture is a good foundation, and the test suite is active. The highest-leverage next move is to make schema setup non-destructive and publication state explicit. Once those two seams are trustworthy, CI, packaging, and catalog generation can safely accelerate the project instead of amplifying operational risk.
