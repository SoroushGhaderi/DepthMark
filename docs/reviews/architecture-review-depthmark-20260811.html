FotMob and Oddspedia should share a naming grammar, not be forced into an identical phase list. The best near-term rule is <verb>_<source>[_<layer-or-entity>].py for globally discoverable entry points, while keeping source-owned implementation modules isolated.

Executive finding

At review time, the repository had two different command organizations: FotMob was mostly grouped by warehouse layer, while Oddspedia is grouped by source and event-intake phase. That is valid internally, but the public command surface was inconsistent and the package CLI pointed four FotMob aliases at nonexistent root-level files. The accepted implementation establishes a source-qualified registry and migrates names through compatibility aliases without introducing a generic provider framework.

Problem

The public interface mixes source-qualified filenames, source-qualified directories, and generic names, so callers must understand implementation layout to select a command.

Solution

Use <verb>_<source>[_<layer-or-entity>] for canonical direct scripts and make the package CLI registry point only to those canonical paths.

  • Interface: source, action, and owned layer/entity are visible without opening the implementation.
  • Locality: a rename is concentrated in one registry, one compatibility map, and documented command tables.
  • Leverage: automation can derive command names consistently across both source domains.
  • Tests: a small registry test can assert path existence, canonical help, and deprecated alias behavior.
Important constraint: identical grammar does not mean identical phases. Oddspedia legitimately has discovery and prioritization; FotMob does not need invented counterparts.

Problem

The layer folders are currently FotMob by convention, but that ownership is not encoded in their names; the Oddspedia exception is documented separately and omitted from the command-surface rule.

Solution

Long term, place source-specific scripts below scripts/fotmob and scripts/oddspedia, with shared quality/maintenance scripts outside both.

  • Locality: a source workflow can be discovered from one subtree.
  • Depth: path ownership carries source context, allowing shorter basenames such as scrape.py and load.py.
  • Migration cost: high; ADR 0002 subprocess paths, tests, and many docs would need coordinated updates.

Problem

The repository intentionally retains wrappers, but documentation and tooling do not all agree on which names are canonical.

Solution

Declare canonical names once, register old names as deprecated adapters, and test that every registry target exists and emits the intended warning.

  • Interface: operators get one documented answer for “which command should new automation call?”
  • Implementation: wrappers remain tiny and can be removed later without changing workflow logic.
  • Seam: the registry becomes the stable place where filesystem paths and package commands vary.

Reporting refinement: one deep observational interface

Implemented · ADR 0025

Status and report are two presentations of the same responsibility, not separate workflows. The canonical seam is now scripts/report_scraping.py (or depthmark report-scraping). It selects fotmob, oddspedia, or all, then renders one common report bundle as a terminal summary, Markdown, or JSON.

Common contract

Discovered, completed, failed, skipped, remaining, progress, artifact count, storage size, and Bronze-admission readiness are comparable across source/date rows.

Read-only boundary

Observation creates no lock, manifest, metrics, run log, source artifact, or warehouse row. Only an explicit --output writes the requested report file.

python3 scripts/report_scraping.py --date 20260301
python3 scripts/report_scraping.py --source fotmob --month 202608
python3 scripts/report_scraping.py --source oddspedia --date 20260301 --format markdown
python3 scripts/report_scraping.py --date 20260301 --fail-on-attention

This is a shared operational Interface, not a provider framework. Source parsing stays in explicit Implementations, preserving the raw-contract boundary and Locality of source-specific changes.

Accepted naming grammar

Use the source suffix at the global script interface, and add the layer or entity when the action would otherwise be ambiguous:

If the team prefers source directories as the primary namespace, the equivalent long-term layout is scripts/fotmob/bronze/scrape.py and scripts/oddspedia/bronze/scrape.py. That is cleaner locally but is a larger migration. Do not use both schemes inconsistently at the canonical interface.

Implemented recommendation

Candidate 1 and Candidate 3 shipped together

The source-qualified grammar is now canonical for mutating source workflows, the package CLI registry resolves those paths, and old script/package names remain deprecated adapters. Cross-source scraping observation is deliberately consolidated behind report_scraping.py. This fixes the runtime defect, makes source ownership legible, and avoids a broad directory move while the Oddspedia Silver/Gold path is still growing.

Suggested sequence
  1. Choose and document the canonical source-qualified names.
  2. Update the command registry and add path/help/alias tests.
  3. Keep compatibility wrappers, but mark only the new names as canonical in README, ADR/runbooks, and AGENTS.md.
  4. Rename or add thin adapters incrementally; update the FotMob orchestrator and all docs in the same change.
  5. Consider the source-folder migration only when Oddspedia Gold commands are being added.
