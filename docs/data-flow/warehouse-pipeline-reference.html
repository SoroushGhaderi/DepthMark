Boundary 1

Bronze = source fidelity

Preserve FotMob and Oddspedia artifacts as-is in their own paths and raw databases. Validate structure and load types without business joins, analytical reshaping, or source mixing.

Boundary 2

Silver = conformed analytics

Standardize keys, types, and entities. FotMob uses deterministic scoped replacement with full-history context; Oddspedia currently publishes the explicit resolution relationship.

Boundary 3

Gold = product outputs

Scenarios and signals materialize business-facing tables. FotMob Gold is implemented; Oddspedia Gold remains a source-owned planned capability.

Ownership

SQL transforms, Python runs

All analytical logic lives in .sql files. Python discovers jobs, executes, validates, and reports. No per-signal Python wrappers.

Idempotency

Safe reruns everywhere

Bronze uses ReplacingMergeTree version convergence; derived layers stage and replace their selected output scope, including rows that stopped qualifying. Rerun the same scope after a partial commit.

Catalogs

Git is truth for metadata

Signal catalogs are markdown frontmatter in Git. MongoDB serves synchronized signal catalog metadata. Analytical product outputs and activations remain in ClickHouse.

Archives

S3 sync is independent

Bronze upload and download are explicit operator workflows. Scraping and warehouse runs never depend on S3 availability.

02UnderstandShared terms, explicit boundaries

A common language for the warehouse

Use these definitions to distinguish source ownership, analytical responsibility, runtime placement, and operational guarantees. Each concept links to its detailed interface or governing decision.

Using these definitions

Read terms in the context of their source owner, output grain, and execution scope. Start with source domain and medallion layer, then follow publication and replacement guarantees. Detailed schema and CLI contracts are linked from Contracts & decisions.

Ownership

Source domain

FotMob and Oddspedia each own their artifacts, raw contracts, conformed entities, and products. Shared infrastructure does not merge their source models or introduce a provider framework.

ADR 0021 & 0023 →
Transformation

Medallion layer

Bronze preserves source fidelity; Silver standardizes source-owned keys and types; Gold materializes business-facing outputs. Each source has all three responsibilities, even where implementation is planned.

Layer responsibilities →
Storage

Historical and Live

Historical contains completed dates. Live is a refreshable snapshot of the machine-local current date. Future collection dates are rejected. Only Historical FotMob artifacts feed Bronze warehouse loading and S3 archive transfer.

Source artifact storage →
Integration

Canonical fixture and resolution

silver.match is the FotMob fixture reference. silver.oddspedia_match_resolution records at most one FotMob fixture per Oddspedia event, with audit evidence; it never rewrites canonical FotMob records.

Silver integration boundary →
Execution

Output scope and input context

The output scope selects the date, month, or full history to replace. SQL may read wider historical context without widening that output scope. Date runs reconstruct their containing monthly partition and preserve unrelated dates.

ADR 0018 →
Reliability

Staging and commit

Stage and validate every selected target before committing the batch. A staging failure leaves targets unchanged. A commit failure can leave a partially committed batch; rerunning the same scope converges safely.

Replacement contract →
Identity

Grain and row identity

Grain describes what one row represents. Ordered row_identity fields identify a signal activation. The v1 hash prefix versions its identity scheme, not the signal's analytical definition.

Activation identity →
Quality

Logical duplicates and physical versions

Logical duplicates violate business identity and fail strict checks. Physical row versions in ReplacingMergeTree are storage diagnostics; compaction is separate maintenance. Engine convergence alone does not remove stale derived rows.

ADR 0019 →
Admission

Published batch

Oddspedia discovery, checksums, manifests, and payload audits gate Bronze publication. Resolution reads only batches marked published in oddspedia_bronze.load_status.

Oddspedia artifact contracts →
Coordination

Date lock and dry run

Mutating Oddspedia commands serialize a sport/date through a cross-process lock. Dry runs do not acquire the lock or mutate state. Loaders expose dry runs to preview their execution plan before publication or replacement.

Script semantics →
Products

Scenario, signal, and activation

A scenario materializes a narrative analytical pattern. A signal materializes a granular detection. An activation enriches a qualifying signal row with identity, metadata, and fixture context in gold.signal_activations.

Gold product surfaces →
Authority

Catalog and serving copy

Git markdown frontmatter owns signal catalog metadata; MongoDB stores synchronized serving copies. ClickHouse owns analytical outputs and activations. A catalog description and a triggered signal row are different kinds of state.

Content & catalogs →
Observation

Scraping report and quality gate

report_scraping.py observes both sources through explicit adapters. Only --output writes a report file. --fail-on-attention turns incomplete/error states into exit 1; warehouse quality checks validate analytical data separately.

Unified reporting →
Recovery

Dead-letter queue and archive

FotMob Bronze failed inserts preserve diagnostic payloads in the DLQ for correction and replay. Optional S3 transfer archives Historical artifacts independently of pipeline success. Neither is a Silver or Gold data layer.

Retention & replay policy →
Runtime

Platform and workflow module

The filesystem holds source artifacts; ClickHouse holds structured Bronze and all Silver/Gold tables; MongoDB holds catalog serving state. Python source modules coordinate workflows and execute SQL; analytical business logic remains in SQL.

Runtime responsibilities →
Maturity

Implemented and planned

Implemented describes an existing interface. Planned describes an architectural responsibility without a complete execution surface. Oddspedia Bronze and Silver resolution are implemented; further Silver entities and its Gold products are planned.

Reference integrity

Fixture reference window

Oddspedia priority planning reads FotMob fixtures for the previous, current, and next date. --silver-reference-window-ready asserts readiness and triggers Bronze/Silver fixture reconciliation; the flag does not prepare missing reference data.

Publication state

Staging, published, and failed

Oddspedia records a date batch as staging before fact-table replacement. Only a completed batch becomes published. A failed publication is recorded as failed when possible; downstream resolution requires the latest state to be published.

Replacement and recovery guarantees

Derived batches calculate and validate selected SQL outputs before committing replacements. Commits occur per table; a failure during commit can leave earlier tables replaced. Fix the failure and rerun the same output scope to converge. A date replacement preserves other dates in that month; explicit full history uses whole-table exchange. These guarantees apply to the selected source-owned path.

Oddspedia publication is a separate admission boundary: downstream resolution requires load_status=published after its fact-table batch completes.

From intake to a resolved fixture

  1. For each target date D, prepare FotMob Bronze and Silver for D−1, D, and D+1. Prioritization verifies fixture reconciliation in that window.

  4. Preview and execute resolution with --silver-reference-window-ready for verified final coverage outcomes. The resolver reads published Bronze only.
