Four axes to keep apart

A source, a layer, a platform, and a product answer different questions. Do not treat them as one thing.

Source domain

Who owns the raw contract? FotMob or Oddspedia. Raw contracts never merge.

Warehouse layer

What transformation applies? Bronze preserves, Silver conforms, Gold materializes.

Runtime platform

Where state lives or computation runs. Platforms never redefine ownership.

Tasks / Load a date

Task · Run

Load a date

Scrape, load, and verify one FotMob or Oddspedia date, with a preview before every write.

FotMobOddspediaPreview before every writeWrites to ClickHouse
FotMob: one completed dateOddspedia: one date to a resolved fixture

FotMob: one completed date

Scrape a completed date, load it through Bronze, Silver, and Gold, then verify. Preview each load first; a dry run writes nothing.

  1. 1
    Scrape the date

    Writes Historical artifacts. Use --today only for a Live refresh.

    depthmark scrape-fotmob 20251208
  2. 2
    Load Bronze

    Preview, then load. Live files are never loaded.

    depthmark load-fotmob-bronze --date 20251208 --dry-run
    depthmark load-fotmob-bronze --date 20251208
  3. 3
    Load Silver

    Replaces only this date inside its month partition. Bronze must be loaded first.

    depthmark load-fotmob-silver --date 20251208 --dry-run
    depthmark load-fotmob-silver --date 20251208
  4. 4
    Load Gold

    Scenarios and signals, then activations if every signal job succeeded.

    depthmark load-fotmob-gold --date 20251208 --dry-run
    depthmark load-fotmob-gold --date 20251208
  5. 5
    Verify

    A clean strict run exits 0.

    python3 scripts/quality/check_data_quality.py --date 20251208 --strict

Needs

ClickHouse running, tables created once, credentials in .env.

If it fails

Rerun the failed command with the same date. Reruns converge. See Fix a failed run.

Done when

Strict quality exits 0 and the date appears in the scraping report.

Shortcut. depthmark run-fotmob-pipeline --date 20251208 runs steps 1 to 4 in one command. It has no dry run. Skip flags are on Orchestration.

Oddspedia: one date to a resolved fixture

Intake, Bronze publication, and resolution are three separate operations. Prepare FotMob Bronze and Silver for D−1, D, and D+1 first.

  1. 1
    Run intake

    Discovery, prioritization, and scraping. The readiness flag verifies the FotMob window; it never creates fixtures.

    depthmark run-oddspedia-pipeline --date 20260301 --silver-reference-window-ready
  2. 2
    Read the report

    Resolve failed or incomplete extraction before publishing.

    depthmark report-scraping --source oddspedia --date 20260301
  3. 3
    Publish Bronze

    Stages the facts and moves the date from staging to published.

    depthmark load-oddspedia-bronze --date 20260301 --dry-run
    depthmark load-oddspedia-bronze --date 20260301
  4. 4
    Resolve fixtures

    Reads published batches only and writes the resolution edge.

    depthmark resolve-oddspedia-events --date 20260301 --silver-reference-window-ready --dry-run
    depthmark resolve-oddspedia-events --date 20260301 --silver-reference-window-ready

Needs

FotMob Bronze and Silver for D−1, D, and D+1, and the Oddspedia tables created.

If it fails

Intake failure: retry the failed step. A refused resolution means the date is not published yet.

Done when

The date is published in oddspedia_bronze.load_status and resolution rows exist.

Tasks / Fix a failed run

Task · Recover

Fix a failed run

Find the failing stage and finish it by rerunning the same scope.

Rerun the same scopeReruns converge
The ruleFind your caseExample: fixing one signal

The rule

Rerun the narrowest failed command with the same scope. Every derived stage is rerunnable, and an identical rerun converges even after a partial commit.

Do not widen the scope to be safe. A wider scope replaces more data than you meant to. Preview with --dry-run first where the command supports it.

Find your case

Failure, first action, and how to finish
FailureFixThen rerun
FotMob scrape blockedRefresh the challenge cookie in Chrome.python3 scripts/refresh_turnstile.py, then re-scrape the dates.
FotMob Bronze loadFix parsing or contracts; failed inserts are in data/dlq/.load-fotmob-bronze --date D --dry-run, load, then reconcile Silver.
Silver or scenario SQLFix the SQL.load-fotmob-silver --date D --dry-run, then the same scope without it.
A signal job failedFix that signal. Activations were skipped.run_gold_sql_jobs.py --id sig_… --date D, then rebuild activations.
Commit failed mid-batchSome tables may be committed; fix the cause.The exact same scope. The publication table shows the state.
Oddspedia refuses a dateIts batch is not published.load-oddspedia-bronze --date D, then resolve.
Reference window not readyPrepare FotMob Bronze and Silver for D−1, D, D+1.Intake or resolution with the readiness flag.
Schema drift reportedSetup never alters tables.recreate_clickhouse_tables.py --drifted, preview first, then --execute and reload the layer.

Example: fixing one signal

The job runner does not rebuild activations, so a corrected signal needs two commands over the same scope.

  1. 1
    Rerun the signal

    Choose one selector: an id, an entity, or a family.

    python3 scripts/gold/run_gold_sql_jobs.py --date 20251208 --kind signal --id sig_team_shooting_goals_efficiency_peak --dry-run
    python3 scripts/gold/run_gold_sql_jobs.py --date 20251208 --kind signal --id sig_team_shooting_goals_efficiency_peak
  2. 2
    Rebuild activations

    Same scope. A bounded scope preserves other dates.

    python3 scripts/gold/activations/build_signal_activations.py --date 20251208 --dry-run
    python3 scripts/gold/activations/build_signal_activations.py --date 20251208

Needs

The date or month that failed, and the layer it failed in.

If it fails

If the same command fails again, read its error and check the service with the health check.

Done when

The failed command exits 0 and strict quality for that scope is clean.

Tasks / Edit a signal

Task · Change

Edit a signal

Change a signal and keep its SQL, catalog, and activations consistent.

GoldWrites to ClickHouse and MongoDB
Change one signal

Change one signal

A signal is SQL, a table, a catalog, and an index entry that change together. Keep the filename, the table, and signal_id identical.

  1. 1
    Edit the SQL

    Signal SQL lives under clickhouse/gold/dml/signals/<entity>/. Keep it deterministic and rerunnable.

    clickhouse/gold/dml/signals/team/sig_team_shooting_goals_efficiency_peak.sql
  2. 2
    Update the catalog

    Edit the frontmatter in scripts/gold/signal/catalogs/. Order in row_identity is part of the identity hash.

    python3 scripts/mongodb/sync_signal_catalogs.py --dry-run
  3. 3
    Change the schema only if needed

    DDL is under clickhouse/gold/ddl/signals/. Setup never alters tables, so apply drift with recreation.

    python3 scripts/maintenance/recreate_clickhouse_tables.py --database gold_signals --table sig_team_shooting_goals_efficiency_peak
  4. 4
    Rerun the job

    Preview, then run for the scope you want to refresh.

    python3 scripts/gold/run_gold_sql_jobs.py --date 20251208 --kind signal --id sig_team_shooting_goals_efficiency_peak --dry-run
    python3 scripts/gold/run_gold_sql_jobs.py --date 20251208 --kind signal --id sig_team_shooting_goals_efficiency_peak
  5. 5
    Rebuild activations

    The same scope, so serving rows match the new output.

    python3 scripts/gold/activations/build_signal_activations.py --date 20251208
  6. 6
    Sync the catalog

    Updates MongoDB only. It does not touch ClickHouse.

    python3 scripts/mongodb/sync_signal_catalogs.py

Needs

The signal id, its SQL file, and its catalog entry.

If it fails

Catalog sync fails if a required key is missing or an asset is outside gold_signals.*.

Done when

Strict quality is clean for the scope, and activations carry the new rows.

Scenarios follow the same loop without activations: SQL, table, catalog entry, then run_gold_sql_jobs.py --kind scenario --id scenario_….

Tasks / Check the warehouse

Task · Verify

Check the warehouse

Run the checks in order and read what each exit code means.

Read-only checks
Five checks, in orderExit codes

Five checks, in order

Each check has its own failure meaning. Stop at the first red one.

  1. 1
    Service health

    Reachability and free disk. Not a data-quality gate.

    depthmark health-check --storage-only --storage data data/fotmob
  2. 2
    Scraping evidence

    Source discovery and scrape state. --fail-on-attention exits 1 on incomplete or error states.

    depthmark report-scraping --source all --date 20251208 --fail-on-attention
  3. 3
    Strict warehouse check

    Logical duplicates and Bronze-to-Silver reconciliation. Physical versions never fail.

    python3 scripts/quality/check_data_quality.py --date 20251208 --strict
  4. 4
    Oddspedia admission

    The date must be published before resolution is trusted.

    depthmark load-oddspedia-bronze --date 20260301 --dry-run
  5. 5
    Catalog validation

    Frontmatter and assets meet the contract. No writes.

    python3 scripts/mongodb/sync_signal_catalogs.py --dry-run

Exit codes

check_data_quality.py returns these codes.

0 · clean

No failures, or only non-strict findings.

1 · failure

Strict mode found logical duplicates or a reconciliation mismatch, or an operational error.

2 · usage

Invalid arguments.

Gold is checked for duplicate identities only. Bronze-to-Gold row parity is not meaningful because Gold applies business rules and different grains. The full gate chain is on Quality.

Daily workflow

  1. PrepareConfigure the runtime, create tables once, confirm service health.
  2. CollectScrape completed dates into Historical. Use --today only for Live.
  3. PreviewDry-run the Bronze, Silver, and Gold loaders for the target date.
  4. RunRun the pipeline, or the layers in dependency order.
  5. VerifyInspect the scraping report, then run scoped strict checks.
  6. PublishSync changed signal catalogs. Archive transfer is a separate task.

Scraping constraints. One match is fetched at a time to protect API reliability. When the API blocks requests, scripts/refresh_turnstile.py refreshes the local challenge cookie. Historical matches are stored compressed (match_*.json.gz). The scraper never touches S3.

Intake to resolution

Intake, Bronze publication, and Silver resolution are three separate operations. Bronze and resolution are implemented. Gold is planned and must not reuse FotMob Gold commands.

Fail-closed rules

Admission is strict on purpose. A date that cannot be verified does not reach Silver.

Discovery accepts complete pagination or a verified empty date, with checksums.

Reference window. Prioritization and the intake pipeline require --silver-reference-window-ready. It verifies the FotMob window and never creates missing fixtures.

Publication. Bronze sets published only after all three fact tables replace.

Resolution reads only published batches. Month and range commands exit non-zero if any date fails.

Publication state

Downstream code can trust a date only when its batch is published. Failed batches are visible, not silently skipped.

Persisted artifacts

The JSON schemas describe the existing shape. Scraped files gain no envelope field, and adopting a contract never rewrites them.

Artifacts and their schemas (schemas/oddspedia/)
ArtifactSchemaCompatibility
match_links.jsonmatch_links.schema.jsonEvent links. An accepted empty inventory stays [].
matches/…/<event_id>.jsonmatch_payload.schema.jsonScore, odds-line, coverage, statistics. Extra compatible fields are kept.

Resolution edge

silver.oddspedia_match_resolution links one event to at most one FotMob fixture, with audit evidence. It is the only cross-source table in the warehouse.

Resolution outcomes
OutcomeMeaning
MatchedOne FotMob fixture is linked.
AmbiguousMore than one candidate; nothing is linked.
UnmatchedThe window is verified and no candidate exists.
Not coveredRecorded only with the readiness flag; the window is verified and the fixture is missing.
UnresolvedWithout the readiness flag, a no-candidate event stays unresolved.

Planned Gold

Oddspedia Gold has no execution surface yet. A new Oddspedia product needs explicit source ownership in its tables, SQL, catalogs, and commands.

Until then, load_fotmob_gold.py must not be used as an Oddspedia substitute.

Scoped replacement

Silver reads all Bronze history as context, but replaces only the selected scope.

  1. Run DMLScripts run in numeric order, 01 to 08.
  2. StageClickHouse calculates and validates each output in staging.
  3. ReplaceREPLACE PARTITION for a date or month. EXCHANGE TABLES for full history.
  4. CheckPost-load contract checks and the summary report.

A date run keeps the other dates in its month. goal, red_card, starters, and match_reference have no current Silver input.

Publication state

silver.scope_publication records each scoped batch, so a partly committed partition is visible (ADR 0028).

How Gold is built

Scenarios and signals read Silver. Only signal outputs feed the activation table.

Job execution

The bulk loader and the selected-job runner share SQL discovery and staged replacement.

  1. Bulk or selectedload_fotmob_gold.py for a scope, or run_gold_sql_jobs.py for chosen jobs.
  2. StageAll selected jobs are staged and validated.
  3. CommitPer table. The bulk loader then rebuilds activations after successful signals.

Activation rebuild

gold.signal_activations is rebuilt for the requested scope. Only full history replaces the whole table.

  1. Scan catalogsActive signals from scripts/gold/signal/catalogs/*.md.
  2. Read identityThe row_identity fields for each signal.
  3. StageActivations for the selected history, built in a staging table.
  4. ReplaceThe scope of gold.signal_activations is replaced. Skipped if any signal job failed.

Identity version. The v1 prefix versions the hash scheme, not a signal definition (ADR 0006). Identity details are on Signals.

Authority flow

MongoDB serves synchronized catalog metadata. ClickHouse keeps the triggered analytical rows. Keep the two apart.

Collections

The sync writes only signals. The other collections are created and indexed by the bootstrap.

CollectionUnique keyPurpose

Sync route

  1. ReadFrontmatter and body of each catalog file.
  2. ValidateRequired keys present, and assets use gold_signals.*.
  3. UpsertInto signals. A SHA-256 content hash makes reruns idempotent.

Preview first. Run sync_signal_catalogs.py --dry-run. It validates and writes nothing.

Two owners. Read catalog metadata from MongoDB. Read triggered analytical rows from gold.signal_activations. A catalog description and a triggered row are different kinds of state.

Orchestration and recovery

Pipeline stages, skip flags, modes, and how to recover from each failure.

FotMob pipeline with skip flagsModesSkip flagsRecoveryScheduling

FotMob pipeline with skip flags

The pipeline runs four stages in order. A failed date skips its downstream stages; other dates may continue.

Modes

The three mode flags are mutually exclusive. --full-history cannot combine with --bronze-only.

Pipeline modes
ModeBehavior
Date or rangeFull route for each date.
--monthScrapes completed dates, then loads Bronze and runs Silver and Gold once for the month.
--full-historyReuses local Historical files, skips scraping. Cannot combine with --bronze-only.
--bronze-onlyScrapes only.
--silver-only / --gold-onlyRuns one layer for the scope. Requires the layer below to exist.

Skip flags

Each skip flag removes one stage. Stages that remain keep their normal writes.

Skip flags
FlagEffect
--skip-fotmobSkips every FotMob stage.
--skip-bronzeSkips scraping. Loads existing Historical files into Bronze.
--skip-clickhouseSkips the ClickHouse Bronze load. Scraping still runs.
--skip-silverSkips Silver.
--skip-goldSkips Gold, including activations.

Naming trap. --skip-bronze skips scraping, not the Bronze load. --skip-clickhouse skips the Bronze load. --bronze-only means scraping only.

Recovery

Rerun the narrowest failed command with the same scope. Identical reruns converge after a partial commit.

Recovery by failure
FailureRecovery
FotMob scrapingRead the report, refresh a challenged token, re-scrape the dates.
FotMob BronzeFix parsing or contracts, preview, reload the date, then reconcile Silver.
Oddspedia scrapeRetry incomplete discovery or failed extraction with the matching selector.
Oddspedia Bronze or resolutionRepair evidence, republish the date, verify the FotMob window, resolve again.
Silver or scenario SQLFix SQL, preview the same scope, rerun the layer or job.
Signal SQL or activationsRerun the signal job, then rebuild activations for the same scope.
Catalog metadataFix the Git catalog, dry-run, then synchronize.
Commit fails mid-batchSome tables may be committed. Fix the cause and rerun the same scope.

Troubleshooting

Date selector rejected

Each family takes its own selector. FotMob scraping takes a positional date or --single-date, not --date. See scope compatibility.

Reference window not ready

Prepare FotMob Bronze and Silver for D−1, D, D+1. The flag verifies; it does not load missing references.

Resolution refuses a date

The latest load_status must be published. Scraping alone does not publish.

Old activations after a fix

Rerun the corrected signal, then rebuild activations for that scope. The job runner does not rebuild them.

Physical versions remain

Expected after a successful run. Check logical duplicates separately. Optimize only after previewing.

Catalog edit, rows unchanged

Catalog sync updates only MongoDB. Rebuild SQL or activations only when the changed assets require it.

Scheduling

scripts/install_schedule.sh writes a host crontab block. scripts/orchestration/run_scheduled_job.py runs named jobs such as fotmob-daily under a lock. Scheduling is external (ADR 0027). Bootstrap installs it unless --no-schedule is passed (ADR 0030).

Gates in order

Each gate has a scope and a different failure meaning. Only the danger gates can fail a strict run.

What each gate proves

Scope and limits
GateProvesDoes not prove
Service healthReachability, storage, free diskArtifact completeness, correctness
Scraping reportDiscovery and scrape evidence, attention statesBronze publication, warehouse validity
Oddspedia admissionComplete discovery, audited payloads, published stateAnything beyond published dates
FotMob qualityLogical duplicates, Bronze-to-Silver reconciliationBronze-to-Gold row parity (Gold has its own grain)

Exit codes

check_data_quality.py returns these codes.

0 · clean

No failures, or only non-strict findings.

1 · failure

Strict mode found logical duplicates or a reconciliation mismatch, or an operational error. Physical versions never fail.

2 · usage

Invalid arguments.

report_scraping.py --fail-on-attention exits 1 on incomplete or error states. Review the report before treating it as acceptance.

Acceptance sequence

  1. HealthCheck service health, preview the loader for the scope.
  2. SourceInspect the scraping report. Resolve incomplete evidence.
  3. CommitConfirm layer commits. For Oddspedia, confirm published.
  4. Strict checkRun FotMob quality with an explicit scope and --strict.
  5. ActivationsAfter signal fixes, rebuild activations and validate catalogs.

Topology

State lives in three places: host files, ClickHouse, and MongoDB. S3 is an optional side channel.

Bootstrap

Run once per host. Setup creates tables only and loads no data. New steps belong in the bootstrap (ADR 0030).

scripts/bootstrap.sh            # server: generated .env, stack, setup, MongoDB, schedule
scripts/bootstrap.sh --local    # local development
scripts/bootstrap.sh --env-only # only prepare .env
scripts/bootstrap.sh --no-schedule

Credentials and ports

Local and production differ on purpose. Never run local credentials in production.
